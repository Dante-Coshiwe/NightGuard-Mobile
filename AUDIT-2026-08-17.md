Everything here was measured against the live project, not read off the code. Where a claim has
a number in it, that number came from a probe run on the day. Re-run the probes rather than

## 1. What was wrong, and is now fixed

### Database — the write path (fixed by migration)

Every one of these failed *silently*. That is the common thread, not the individual policies.

| Symptom | Cause | Fixed by |
|---|---|---|
| A shift retried since 2026-08-14, never saved | `shifts`/`ob_entries`/`incidents` had no SELECT policy that resolved | `20260817_read_policies.sql` |
| Patrol coverage computed off 26% of the scans | `nfc_scans` SELECT was `guard_id = auth.uid()`, and the app writes `guard_id` NULL by design — 342 of 461 rows invisible | same file (nfc_scans added later, needs the re-run) |
| A new handset could not register | `devices` missing from the write-policy table list | re-run of `20260814_write_policies.sql` |

**The mechanism is worth understanding, because it will recur.** `startShiftRecord`,
`createObEntry`, `createIncident` and `persistPatrolScan` all end in

```js
.insert(payload).select('*').single()
```

`.select()` after an insert makes supabase-js send `Prefer: return=representation`, which
PostgREST runs as `INSERT ... RETURNING`. **`RETURNING` is a read.** It is filtered by the SELECT
policy, and when that policy matches nothing PostgreSQL raises 42501 and **rolls the INSERT back**.
Nothing is written, and the client is told `new row violates row-level security policy` — which
reads like a *write* permission problem and is not one.

Isolated on the live project, same payload, same user, one header apart:

```
POST /rest/v1/shifts                                  -> 201 Created
POST /rest/v1/shifts   Prefer: return=representation  -> 403  42501
```

So: **a missing READ policy silently destroys WRITES.** Any new table the app writes needs
INSERT, UPDATE *and* SELECT, or it will look like a write bug forever.

### Database — the dashboard (fixed by migration)

All 18 of the dashboard's Supabase operations were inventoried and probed. Seven were broken:

| Operation | Was | Now |
|---|---|---|
| Create organisation | 403 42501 | OK |
| Create location | 403 42501 | OK |
| Rename location | **204, row unchanged** | OK |
| Accounts page | 1 of 29 profiles | 29 of 29 |
| Edit an account | 200, 0 rows | OK |
| Delete an account | 200, 0 rows | OK, with guards |
| Audit trail | 403 42501 | OK |

The rename is the one to remember. `index.html:3460` is `.update(payload).eq("id", siteId)` with
no `.select()`, and the handler only tests `error`. With no policy whose **USING** clause matches,
the statement updates zero rows and PostgREST answers **204 with no error** — so the dashboard
toasted "Location updated", reloaded, and redrew the old name. A rename that reports success and
does not happen is worse than one that fails, because every export label and site filter reads
that name.

Fixed by `20260817_02_admin_site_management.sql`, which also adds a trigger granting each new
site to every admin — removing the standing `node scripts/grant-all-sites.mjs` step. That manual
step was the same failure mode as everything above: an access row nobody wrote, failing silently.

### App (fixed in bundle 1.1.28 / APK 1.26)

1. **An RLS refusal was thrown away instead of queued.** `throwSupabaseError()` flattened every
   Supabase error to HTTP 400. `useOfflineApi.shouldQueueFallback()` routes **403** into the outbox
   and lets **400** throw — so the one status meaning "retry once somebody fixes the policy" was the
   one status dropped at the call site. Now 42501 maps to 403; `classifySyncFailure()` still counts
   it so it dead-letters and the banner tells somebody.
2. **A failed checkpoint scan reached no store at all.** `persistPatrolScan()` let the throw escape
   and all three callers only `console.warn`. `markCheckpointReached()` has already run by then, so
   the guard is shown "points gathered" for a checkpoint on no server, in no queue, in no
   dead-letter list. It now hands the scan to the outbox itself.
3. **A queued photo was stored twice in the same quota.** `PedestrianTab`/`VehicleTab` cached the
   local data URL while the same bytes sat in the queue as `_pendingPhoto`. Both are localStorage,
   and `saveQueue()`'s only failure handling is a `console.error` — so a quota exception while
   registering one visitor silently discards the **entire outbox**. Bytes now live in the queue
   alone; the cache carries `_pendingPhotoCount`, the rule incidents have followed since 08-13.

## 2. Still open

Ranked by what it costs when it happens. None of these were introduced today; all are confirmed
present in 1.26.

### a. `exit_time` is stamped at sync time — **data is wrong, not missing**

[api.js:681](src/services/api.js#L681). Proven on the day: exit tapped **13:06Z**, recorded
**13:49:35Z**. A visitor's departure time is wrong by however long the handset was offline, and
nothing marks it as approximate. Same class as the `endShiftRecord` bug already fixed by writing
`payload.ended_at` — the fix is the same shape.

### b. The native patrol drain is at-most-once

`PatrolBuffer.drain()` returns the walk and clears it inside the same `synchronized` block; between
that and the JS write the walk exists only in a variable. A process kill there loses it — on the one
path built for a pocketed phone with the screen off, where kills are *expected*, not exceptional.
Needs a two-phase drain: hand over, let JS persist, then acknowledge and clear. Do not "fix" it by
removing the clear — without one, every drain re-delivers the whole walk and the trail duplicates.

Related: `PatrolBuffer.read()` returns `empty()` on unparseable JSON and has **no `.bak`**, while
the JS [atomicFile.js](src/lib/atomicFile.js) keeps a backup and recovers. The half of the system
most likely to be killed mid-write has the weaker recovery.

### c. Kiosk wedge on install or force-stop — **reproduced 3× on 2026-08-17**

Installing over a running kiosk-locked app, or force-stopping it, leaves the device pinned to a
task that no longer exists:

```
mLockTaskModeState=PINNED
  Task{… com.nightguard.nightguardtrack … sz=0}    <- pinned task, zero activities
E ActivityTaskManager: Attempted Lock Task Mode violation
```

Nothing will launch afterwards, and `am task lock stop` replies *"Activity manager is not in
lockTaskMode"* — the two states disagree, which is why nothing can clear it. **Only a reboot
recovers.** Operationally: after installing on a handset, **reboot it** before handing it back.

### d. `flushPersistNow()` is not awaited

Including on `appStateChange(false)` and `pagehide` — the last moment before Android may kill the
app. The write can still be in flight when the process dies.

### e. The outbox is uncapped, and every write rewrites the whole store

`nightguard_offline_queue` is in `CRITICAL_KEYS`, so every mutation serialises the entire storage
state to one file. The cost of saving any record grows with how much is already queued, on the
device least able to afford it.

### f. `device_sync_logs` — app writes them, app cannot read them

76 of 76 rows hidden from the app account. Harmless today because nothing reads them back, but it
is the same read-policy gap as §1, so it will bite the moment anything tries to display sync
history. `ota_update_logs` UPDATE is likewise refused — correct as-is, the app only inserts.

### g. Not verified

- **Plural wording of the dead-letter banner** ("2 records… They are… they will"). Singular is
  verified on-device with a real rejected record; the plural branch has never rendered.

## 3. Schema facts — columns that do NOT exist, and ones that trip you

Verified 2026-08-17 from the live PostgREST OpenAPI spec.

### Columns that do not exist (selecting them returns 400)

| Table | Missing | What to use instead |
|---|---|---|
| `patrols` | `ended_at` | **`actual_end`** (and `actual_start`) |
| `patrols` | `checkpoints_completed`, `total_checkpoints` | **Derived at read time** in [api.js:354-355](src/services/api.js#L354-L355) from `getPatrolCheckpointCounts()`. `patrolSession.js` puts them in the *local cache* object only — that is free-form JSON and is NOT a bug |
| `shifts` | `duration_hours`, `duration_minutes`, `duration_ms`, `is_sunday` | Derived in [shiftAnalytics.js](src/lib/shiftAnalytics.js). Nothing has ever written them |

### NOT NULL columns that will 23502 you

| Table | Required (NOT NULL, no default) |
|---|---|
| `audit_log` | `id`, `table_name`, **`record_id`**, `action`, `created_at` |
| `shifts` | `id` (has a default — see the probe warning below) |

`audit_log.record_id` is the trap: an audit write without it fails `23502`, which looks like a
permission problem in passing but is not.

### Columns that exist but are dead

- **`ob_entries.entry_text`** — exists; the app writes the occurrence into
  `nature_of_occurrence`. 0 rows have ever had an `entry_text`.
- **`incidents.picture_url` / `photo_urls`** — both **EXIST**; the 2026-08-13 incident-photos
  migration has been applied. `createIncident`'s `PGRST204` fallback is therefore dormant, and
  should stay as-is for devices that predate it.

### `patrol_checkpoints.tag_uid` — unique **per site**

Confirmed by saving the same tag at two different sites (both accepted), and the same tag twice at
one site (`409 / 23505`). Two GPS-only points both save when `tag_uid` is **NULL**; they collide if
it is an **empty string**. [schemaData.js:494](src/services/schemaData.js#L494) already normalises
blank → `null`, dedupes within a batch, and retries GPS-only on collision.

## 4. Probe technique — read this before writing one

**A bare PostgREST POST returns 201 with an empty body on success.** "Empty response" means it
inserted. On 2026-08-17 a probe that omitted `id` expecting a NOT NULL failure instead created
**8 junk rows across 7 tables**, because `id` has a `gen_random_uuid()` default. PostgREST's
OpenAPI `required` list is not a reliable guide to that.

Use one of these instead:

- Send `Prefer: return=representation`, capture the returned `id`, and **delete it immediately** in
  a `finally` block. Then sweep for a marker string to catch anything that leaked.
- Or make the row fail a constraint *after* RLS passes, so a pass shows up as `23502`/`23505` and
  writes nothing — but only if you have verified which column actually lacks a default.

For UPDATE, rewrite one existing column to the value it already holds: that exercises USING,
WITH CHECK and the RETURNING read-back without changing data.

Two ready-made probes live in the scratchpad from this session: a write matrix over all eight
app-written tables, and a config/admin matrix. Both clean up after themselves and both print a
leftover count. Re-run them after **any** schema change or new site.
